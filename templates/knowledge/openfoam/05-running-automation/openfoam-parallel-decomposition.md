# OpenFOAM 串并行运行、区域分解与结果重构

并行计算首先要保证与串行结果在允许误差内一致，然后才追求加速。进程数不是越多越快：单进程单元过少时，通信与 I/O 会主导，并行反而更慢。本文给出从串行基准到分解、运行、重构与扩展测试的完整工程流程，并给出可量化的效率判据。

## 1 结论与适用场景

- **前提**：并行与串行在允许误差内一致，然后才谈加速比。
- **结论**：实际收益由两项共同决定——分解质量（负载均衡且接口面积小）与 I/O 策略。
- **适用**：网格量大、时间步多、需要参数扫描的工程算例。
- **不适用**：小网格（单进程几千单元以下）或通信受限的共享内存机器，此时串行或少量进程更划算。
- **经验法则**：单进程单元数低于约一万时，通信开销容易超过并行收益，需要谨慎评估。

**判断口诀**：并行前先问三件事——串行结果是否已稳定、通信能否被计算量摊薄、I/O 会不会成为瓶颈。三者都“是”，加速才可能有意义。

**适用边界**：网格量大、每步计算重、单机能耗高时收益最大；小算例或强耦合（如大范围压力耦合）的算例，并行收益有限甚至为负。

**核心命题**：并行求解的价值不在于“跑得动”，而在于在可接受误差内把墙钟时间压到最低，本质是一道性价比优化题。**常见误解**：以为核数越多越快；实际超过一定规模后，通信与 I/O 会吃掉全部收益。

## 2 背景与原理

区域分解把网格切成 $N$ 个子域，每个子域由一个 MPI 进程拥有。子域交界生成 processor patch，用于每一步交换 halo 层数据，因此通信量近似正比于**接口面积**，而与子域内部单元数关系不大。

常用分解方法：

- **simple**：按几何方向切块，简单可控，适合结构网格，但若方向选错会切出巨大接口；
- **hierarchical**：按方向与比例逐级切分，可指定各方向权重，适合已知主流方向的情形；
- **scotch / metis**：图分区方法，以最小化接口为目标，通常负载更均衡，适合复杂几何。

权衡：接口越小，通信越少；但图分区本身有开销，且不同分解会让浮点归约顺序不同，产生微小的结果差异。分解前应尽量让接口避开强梯度区与强耦合区。

**通信量的估算**：每步都要在接口两侧交换一层 halo 数据，通信量近似正比于接口面积与交换场数，而与子域内部单元数关系不大。因此把接口切得细碎、或让接口穿过细密网格区，都会让通信开销迅速上升。分解时优先选择与主流方向一致的切分面，避免在同一方向上切太多刀。

**接口与精度的关系**：halo 数据交换本身不引入物理误差，但接口位置会改变浮点求和顺序，使并行结果与串行存在微小差异；只要差异不随时间放大，就属正常。若接口穿过分离区或强梯度区，差异更易被放大，应主动避开。

**processor patch 与后处理**：分解后每个进程目录下有独立的网格与场，接口以 `procBoundaryXXXtoYYY` 形式命名。后处理通常在重构后的统一网格上进行，因此 `reconstructPar` 是并行工作流的常规收尾步骤。**分解的可逆性**：decomposePar 只是把网格与场切分，原网格仍保留在 `constant/polyMesh`；重构后即可回到串行目录结构，不影响物理结果。

## 3 关键配置与公式

`system/decomposeParDict` 关键字段：

```text
numberOfSubdomains 8;
method             scotch;

// 结构网格也可选几何类方法：
// method simple;
// simpleCoeffs { n (2 2 2); delta 0.001; }

// 或按方向加权切分：
// method hierarchical;
// hierarchicalCoeffs { n (4 2 1); delta 0.001; order xyz; }

distributed      false;
preservePatches  ();
```

`distributed true` 用于分布式内存上的超大规模分解，一般单机算例保持 `false`；`preservePatches` 列出不希望被切开的面，例如需要整体处理的特殊耦合面。`hierarchicalCoeffs` 的 `n` 给出各方向切分数、`order` 指定切分顺序，方向权重不合理会直接抬高接口面积。

核心性能指标。加速比与并行效率：

$$
S(N)=\frac{T_1}{T_N}, \qquad E(N)=\frac{S(N)}{N}
$$

负载不均衡度（$I=1$ 为完美均衡）：

$$
I=\frac{\max_i N_i}{\bar N}, \qquad \bar N = \frac{1}{N}\sum_{i=1}^{N} N_i
$$

计时模型（$T_c$ 为通信与 I/O 开销）：

$$
T_N = \frac{T_1}{N} + T_c
$$

它解释了为何存在最优进程数：$N$ 增大时 $T_c$ 占比上升，总时间可能不降反升。若串行比例为 $f$，Amdahl 定律给出加速上限：

$$
S(N) = \frac{1}{f + (1-f)/N}
$$

例如 $f=0.05$，即使 $N\to\infty$，$S$ 也只趋近 20。据此可判断继续加核是否还有意义。

**扩展测试的做法**：固定网格与时间步，分别用 1、2、4、8 核跑相同步数，记录每步墙钟时间；把 $T_N$ 与 $S$、$E$ 列入表格，找出效率跌破约一半的核数，那就是本算例的实用上限。

**并行效率的经验区间**：$E$ 在 0.8 以上通常值得用，0.5 到 0.8 需权衡，低于 0.5 说明通信已占主导，继续加核意义不大。这个判断依赖于问题规模，规模越大越容易保持高效率。

## 4 工程做法与参数

- **选方法**：结构或分区明显的网格用 `simple` / `hierarchical`；复杂几何用 `scotch`。避免用 `simple` 把接口切得过大。
- **分解数等于核数**：`numberOfSubdomains` 必须与 `mpirun -np` 一致，否则报错或空跑。
- **一致性验证**：用同一网格、字典与时间步，分别跑短串行与短并行，比较守恒量、残差趋势与目标量。浮点归约顺序会造成微小差异，但不应导致宏观分叉；若差异持续放大，要检查问题敏感性与并行边界。
- **I/O 策略**：高频写出大量小文件会压垮共享文件系统。只写必要场与时间，优先使用 `collated` 或二进制文件处理器，重构前估算磁盘空间。
- **负载均衡检查**：用 `decomposePar -cellDist` 生成单元分布场，在 ParaView 中确认各分区大小接近、没有把全部边界层挤进单个进程。
- **性能报告**：记录硬件、核数、MPI 版本、单元数、每步时间、总耗时、写出频率与分解方法；至少做 1、2、4、8 核的短扩展测试，选总成本最低的配置。
- **重用与重启**：分解结果可保存复用，避免每次重跑都分解；重启（restart）时应确认分解方式与之前一致，否则接口布局变化会引入差异。
- **日志检查**：并行求解后查看 `log.parallel`，确认没有 processor patch 相关初始化告警。
- **时间步协调**：并行不改变时间步算法，但为保持目标 Courant 数，可能要一致地调整 `maxCo` 与 `adjustTimeStep`。

**分解数怎么定**：先用 1、2、4、8 核做扩展测试，取效率仍高且总耗时最低的核数，再结合可用内存与队列限制。不要一次跳到几十核，那样既浪费机时又难定位瓶颈。**集群上用**：通过调度器提交，请求核数与 `numberOfSubdomains` 严格对齐；作业脚本里先分解、再 mpirun、最后重构，形成闭环。分解与重构都应在同一 MPI 环境下进行，避免版本不一致带来的接口差异。

## 5 可复现示例

```bash
# 1) 短串行基准
foamRun -case . 2>&1 | tee log.serial

# 2) 分解（-force 覆盖旧分解，-latestTime 只处理最新时间）
decomposePar -force -latestTime 2>&1 | tee log.decomposePar

# 3) 并行运行（核数须等于 numberOfSubdomains）
mpirun -np 8 foamRun -parallel -fileHandler collated 2>&1 | tee log.parallel

# 4) 重构场到统一时间目录
reconstructPar -latestTime 2>&1 | tee log.reconstructPar

# 5) 仅在网格随计算改变时重构网格
reconstructParMesh -constant 2>&1 | tee log.reconstructParMesh
```

`reconstructPar` 可用 `-time 100:200` 指定时间范围、`-fields` 指定场，避免一次重构全部数据；重构完成后确认目标量曲线与串行基准一致；若不一致，先排除分解方式与写出频率的差异，再怀疑物理设置。串行与并行的残差曲线应大体重合；若并行在接口处出现周期性振荡，多为分解不当或非正交修正不足。

## 6 常见坑与排查

- **核数与 `numberOfSubdomains` 不一致**：报错或进程空跑。
- **忘记重构**：只看 `processor*` 目录，后处理找不到统一结果。
- **单进程单元太少**：通信与 I/O 主导，并行比串行还慢。
- **`simple` 方向不当**：接口面积巨大，通信量爆炸。
- **负载失衡**：某个进程单元远多于其他，整体被最慢进程拖住。
- **I/O 瓶颈**：写文件时间超过求解时间，应降低写出频率或改用 collated。
- **浮点差异被误判为错误**：并行与串行有微小差别是正常的，宏观分叉才是问题。
- **重启时换了分解**：`processor*` 布局与上次不同，续算结果出现跳变。
- **只加核不测效率**：核数翻倍但耗时没下降，说明已进入通信或 I/O 主导区。
- **分解方向与网格无关**：想当然地按几何外侧切分，忽略了贴壁加密带来的负载不均。
- **接口穿过周期面**：周期与 processor 边界处理不当会引入不一致。
- **重构时遗漏场**：只重构部分场，后处理调用缺场报错，需明确要重构的场清单。
- **共享内存机器盲目加核**：内存带宽饱和后加核反而变慢，需实测确认。
- **重启时残留旧 `processor*` 目录**：旧分解与新分解冲突，导致读入错乱。

## 7 检查清单与参考

1. 是否先建立了串行基准并做过并行一致性对比？
2. `numberOfSubdomains` 是否等于 MPI 核数？
3. 各分区单元数是否均衡，接口面积是否合理？
4. 是否做了 1、2、4、8 核的扩展测试并记录每步时间？
5. I/O 处理器与写出频率是否适配共享文件系统？
6. 是否用 `reconstructPar` 重构并核对目标量？
7. 是否用 `-cellDist` 检查过分解分布？
8. 性能报告是否记录了硬件、MPI、分解方法与单元数？
9. 重启或续算前，是否清理并确认了 `processor*` 目录？
10. 扩展测试是否给出了效率曲线与推荐核数？
