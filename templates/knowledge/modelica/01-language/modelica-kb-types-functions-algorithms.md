# Modelica 类型、单位、数组、函数与 algorithm

## 1. 结论与适用场景

类型和单位是模型接口的一部分，而不是可有可无的注释。优先使用 `Modelica.Units.SI` 中的类型，并设置合理的 `min`、`max`、`nominal`、`start` 与 `displayUnit`，能让工具在仿真前发现量纲与尺度问题，而不是等到结果发散才回头排查。

`function` 适合封装确定的输入—输出计算：多项式物性、插值表、查找与反查、几何参数计算、经验关联式。它们没有内部状态，输出完全由输入决定，因此可以安全地在方程中反复调用并参与符号求导。`algorithm` 则用于确实需要顺序逻辑的场合，例如带分支与循环的数据处理、逐项赋值与累加。

选择原则可以概括为三句话：能用方程表达的关系就不要用算法；能在函数里封装的重复计算就不要内联到组件里；只有当逻辑无法用关系式表达时，才引入 `algorithm`。这条原则能最大限度保留模型的声明式特性，让工具自由重排、求导与并行化。

需要强调的是，类型与单位不是装饰，它们参与工具的结构与量纲检查。一个没有单位的模型即使数学上能求解，也无法在接口层面阻断把温度当压力、把热流量当质量流量的错误。同理，把重复计算封装成带明确输入输出类型的函数，既能让主模型更短，也能让这些计算被单独测试。本节适合需要处理物性关联式、实验数据插值、多组件阵列以及带分支逻辑的工程建模与仿真的读者。

## 2. 原理与语言语义

先看类型系统。`type` 可基于基础类型定义专用物理量，从而让单位、范围与语义绑定在同一个名字上；`enumeration` 适合表达有限模式（如边界类型、流态），比用整数更安全、更可读；`record` 适合打包参数集合或结果结构。它们的共同价值是把"含义"写进接口，而不是散落在注释里。

数组为分布参数与多组件系统提供了紧凑表达。数组方程整体参与方程系统，循环生成的是一组方程而不是时间顺序的执行。维度应尽量由参数静态确定，并用 `size()`、切片和向量化操作减少索引错误。数组的每一维都对应一个离散指标，理解这一点有助于写出可读的索引表达式。

`function` 有严格的纯计算边界：内部变量是局部的，输入通过位置或名称传入，输出用 `output` 声明。函数不应读写全局变量，也不应产生副作用。若函数涉及积分或状态，应改用模型或方程而不是函数。`algorithm` 中的 `:=` 是按顺序执行的赋值，与 `equation` 中的 `=` 语义不同；算法段整体参与方程系统，对同一个输出的多次赋值最终形成一个定义，因此不能按等号出现次数来判断结构平衡。

这类结构本身不引入方程，它们只影响类型与参数组织，不应被用来隐藏物理关系。`record` 与 `enumeration` 的恰当使用能显著提升可维护性：把一组相关参数（如几何尺寸、效率曲线系数、控制器限幅）打包成 `record`，可以让接口签名保持稳定，新增字段时不必修改所有调用点；用 `enumeration` 代替整数开关，既能防止非法取值，也能让选项在图形界面中自解释。

## 3. 关键公式与语法

函数的语义是一个映射：

$$
y = f(u)
$$

当函数出现在方程中而工具需要对其求导时，应按链式法则传播导数：

$$
\frac{d y}{d t} = \frac{\partial f}{\partial u} \frac{d u}{d t}
$$

若函数包含不可微或分段定义的分支，工具可能无法得到连续导数，从而影响事件定位与求解稳定性。此时应通过 `smooth` 或显式的事件机制表达不连续点。

数组方程常用于把线性系统紧凑地写入模型，离散后本质是

$$
A x = b
$$

其中矩阵与向量维度由参数决定。分段线性插值是工程中最常见的函数形式，其内部可写为

$$
y(x) = y_i + \frac{y_{i+1} - y_i}{x_{i+1} - x_i} (x - x_i), \qquad x_i \leq x \leq x_{i+1}
$$

对应的导数区间为常量斜率，便于工具在连续区间内直接求导。这些关系都适合封装进函数，让主模型保持简洁。

需要区分两类不连续：物理上真实存在的切换（如阀门开闭、相变点）应作为事件处理，让求解器在切换点精确停步；而只是数据拟合造成的拐点，则应尽量用连续或可微的形式描述，避免不必要的步长扰动。这种区分直接影响求解效率与事件定位精度。

## 4. 工程做法与参数

类型与属性方面，为每个物理量声明 SI 单位与 `quantity` 描述；对可能为零或负的量正确设置 `min`（例如绝对温度应大于零）；对跨数量级的变量设置 `nominal`，帮助求解器做残差缩放。`start` 主要是初值猜测，只有与固定属性或初始方程配合时才构成强约束，不要把 `start` 当作边界条件使用。

数组方面，优先用参数固定维度，例如 `parameter Integer n = 8;` 配合 `Real u[n];`，避免运行期改变维度导致方程结构不确定。用 `sum()`、`size()` 与切片替代手写索引循环，可读性更好也更少出错。

函数方面，为需要求导的连续函数提供解析导数注解，或让其实现是工具可微分的表达式；避免在函数内部使用全局量或修改外部状态。若必须调用外部 C 代码，应通过 `external` 声明并保证线程安全与无副作用。数值尺度上，不要靠随意乘系数或无量纲化常数来掩盖求解器的缩放问题，而应用 `nominal` 显式表达典型量级。

工程上还应把函数当作可版本化的接口来管理：输入输出的含义、单位与有效范围应写清，并在越界时给出提示或钳位策略。当多个模型共享同一条关联式时，应避免复制粘贴出多个分叉版本，而应集中于一处维护。对于需要高精度求导的关联式，可用多项式或分段多项式替代查表，并利用 `smooth` 标注其连续阶数，以提升求解器对导数的信任度。

## 5. 可复现示例

下面给出一个带解析导数的分段线性插值函数，以及它在模型中的调用方式，随后是数组方程的紧凑写法。

```modelica
function tableLookup
  input Real x;
  input Real xTab[:];
  input Real yTab[:];
  output Real y;
protected
  Integer i;
algorithm
  i := 1;
  while i < size(xTab, 1) and x > xTab[i + 1] loop
    i := i + 1;
  end while;
  i := min(i, size(xTab, 1) - 1);
  y := yTab[i] + (yTab[i + 1] - yTab[i])
       / (xTab[i + 1] - xTab[i]) * (x - xTab[i]);
end tableLookup;

model TableSource
  parameter Real xTab[:] = {0, 100, 200, 400};
  parameter Real yTab[:] = {1.0, 1.5, 3.0, 5.0};
  Real x(start = 0);
  Real y;
equation
  der(x) = 10;
  y = tableLookup(x, xTab, yTab);
end TableSource;
```

数组方程的紧凑写法如下，系数矩阵与右端项都由参数给出：

```modelica
model LinearSystem
  parameter Integer n = 3;
  parameter Real A[n, n] = [2, -1, 0; -1, 2, -1; 0, -1, 2];
  parameter Real b[n] = {1, 0, 1};
  Real x[n];
equation
  A * x = b;
end LinearSystem;
```

运行时可把结果导出为 CSV 以便与解析解比较：

```bash
omc -s simulate-system.mos
```

## 6. 常见坑与排查

第一类坑是把 `algorithm` 当方程来数个数。算法段中同一输出被多次赋值仍只对应一个定义，若按文本顺序或等号数量推断平衡，会得到错误结论。

第二类坑是分段函数在连续方程中使用却不声明平滑性。斜率突变处若未作为事件处理，会造成步长急剧缩小或求解失败；应明确区分"需要事件插值"与"可平滑过渡"两类不连续。

第三类坑是函数隐藏状态或副作用，例如在函数内读写全局变量、使用静态缓存。这会让输出不再由输入唯一决定，破坏方程的可重排性与可逆性。

第四类坑是数组维度在运行期变化，或索引越界。应尽量让维度静态可定，并用断言或范围检查捕捉越界。

第五类坑是单位换算被藏在常数里。与其在函数里乘一个含单位系数的魔数，不如用带单位的类型让检查器替你核对。此外，忽视 `nominal` 会让量级相差悬殊的方程在统一绝对尺度下被忽略。

第六类坑是插值超出表格范围时静默外推。若不显式处理两端边界，函数可能给出物理上不合理的结果；应在内部钳位或报错，而不是让错误静默传播。第七类坑是函数内部使用可变大小的临时数组或递归，导致工具无法确定方程规模，从而难以生成高效的求解代码。第八类坑是把带循环的算法写成依赖于未定义顺序的累加，从而在不同工具下得到不同答案。排查这类问题时，应把函数单独取出，用一组已知输入输出验证其确定性与边界行为。

## 7. 检查清单与参考

建模中：优先使用 SI 类型并声明合理属性；数组维度尽量静态；函数保持纯计算并避免副作用；分段关系明确平滑性。

实现时的一个重要习惯是：把每个函数都当作未来别人（包括未来的自己）会调用的公开接口。参数名应自解释，避免用 `a`、`b` 这类无法传达单位与含义的符号；同时为一个函数维护一组最小测试点，涵盖端点、极值与正常工况。这能在重构时快速发现意外改变。

验证时：检查函数在区间端点与边界处的取值；用解析解验证插值与线性系统；确认算法段未破坏结构平衡；检查单位与 `nominal` 是否合理。

交付前还应确认：函数的输入输出含义、单位与有效范围已写明；越界行为明确；关联式集中维护而非多处复制；数组维度不依赖运行期取值。
