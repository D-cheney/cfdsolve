# Modelica 事件、混合系统与 CFD 降阶耦合

阀门切换、控制逻辑、饱和、碰撞与相变都会引入离散事件，使系统成为在连续积分与离散切换之间交替的混合系统。当系统模型再通过特性图或降阶模型（ROM）接入 CFD 结果时，事件还会与耦合接口相互作用：切换时刻、通信步长与守恒量三者若不同步，就会出现不物理的跳变。本文聚焦这种“事件—耦合”交界面的建模与排查。

## 1. 结论与适用场景

先判断一个不连续现象是“真实物理事件”还是“关联式的分段”。只有真正改变系统模式的切换才应建成事件；把每条分段关联式都变成事件，会制造大量零交叉，显著拖慢仿真并降低鲁棒性。

- 需要事件：阀门开闭、控制器模式切换、相变压力的饱和、安全阀启闭、碰撞与接触。
- 不宜建成事件：物性随温度的分段拟合、特性图的分片插值；这些应通过光滑插值或 `smooth()` 处理。
- 与 CFD 耦合时：事件往往对应工况切换（泵启动、风机变速），此时 ROM 或特性图的工作区间随之改变，必须保证切换与耦合接口同步。

分层上，CFD 信息进入系统模型的成本从低到高为：经验关联式、稳态特性图、动态降阶模型、运行时联合仿真。事件越频繁、越接近系统主导时间尺度，就越需要高保真、且需要事件与耦合点严格对齐的层级。

工程上还有一个务实原则：能用连续光滑描述的就不要用事件。例如风机效率随转速的变化，用一张光滑特性图比“低速档/高速档”两个离散模式更接近真实，也避免了切换抖振。只有物理上确实存在开关、饱和或碰撞，才值得付出事件带来的额外求解与同步成本。因此，建模时应对每个不连续点追问一句：它真的改变了系统方程结构吗？

## 2. 原理与协议/语义

混合系统由连续 DAE 与离散状态共同描述。事件分三类：时间事件在预定时刻或 `sample()` 触发；状态事件由连续表达式过零触发；采样事件按固定周期更新离散控制器。`when` 用于离散赋值，`pre(...)` 读取事件前的值，`reinit(...)` 可在事件时刻重置连续状态。

事件发生时会进行事件迭代：工具在事件时刻重新求解离散方程与代数约束，直到一致。若离散方程互相关联，迭代可能需要多轮。`noEvent` 则关闭对某表达式的零交叉监测，使工具把它当普通表达式处理——只有在忽略该不连续性不改变物理语义、且不会跨过阈值时才可安全使用，绝不是用来“消掉报错”的开关。

事件迭代的正确性还依赖离散量的一致性。`when` 中更新的每个离散变量都应是“边沿触发”的，即只在条件首次为真时赋值；重复赋值会破坏事件语义。`pre(...)` 保存事件发生前的值，用于在关系式内部引用上一状态，是构建滞回与状态机的关键工具。离散状态一旦确定，其取值在两次事件之间保持不变，这保证了段内连续、段间切换的清晰结构。

与 CFD 耦合时有两处额外要求。其一，切换时刻与耦合通信点必须对齐：若通信步长跨过一个事件，ROM 在该步内用的是切换前的工况，输出会滞后或跳变。其二，`reinit` 会改变连续状态，而 ROM 往往依赖这些状态或对应的工况标签；重置后必须重新建立 ROM 与其内部状态的一致性，否则会出现质量或能量不闭合。

从数值角度看，事件会把连续问题切成若干段，每段内光滑、跨段则不光滑。求解器必须在事件时刻重启积分，因此事件越多、重启越频繁，步长控制的开销越大。这就是“隐藏事件”——由未加 `smooth()` 的分段表达式隐式生成——会让仿真莫名变慢的原因。

## 3. 关键公式与接口

滞回用两个不同阈值避免在单点反复切换。设离散状态 $s$，控制量为 $T$，则

$$ T_{low} < T_{high}, \qquad s^{+} = 1 \ \text{若}\ T \geq T_{high}, \qquad s^{+} = 0 \ \text{若}\ T \leq T_{low} $$

在两个阈值之间时保持原值 $s^{+} = s^{-}$。状态事件由零交叉条件刻画：

$$ g(t_e) = 0, \qquad \dot{g}(t_e) \neq 0 $$

其中 $g$ 是事件指示表达式。当 $g$ 在噪声下频繁变号时，就发生抖振；可用最小驻留时间 $t_{dwell}$ 限制事件频率：

$$ t_{e,k+1} - t_{e,k} \geq t_{dwell} $$

`reinit` 造成的状态跳变必须与守恒一致。若某储能状态在事件处被重置，则被“丢弃”或“注入”的能量为

$$ \Delta E = E\!\left(x^{+}\right) - E\!\left(x^{-}\right) $$

它应当对应真实的物理过程（如阀门突开引起的能量注入），否则就是数值人为产物，需要在界面处补齐。最后，事件与耦合通信点的同步条件可写为

$$ \Delta t_{comm} \leq t_{e} - t $$

即通信步长不应跨过事件时刻，必要时在事件处强制截断步长。

上述几条共同说明：事件耦合的风险集中在“时间对齐”与“状态一致”两点。前者要求通信步长不跨越事件，后者要求重置状态后立即重建耦合模型内部的一致性；两者任一缺失，都会表现为结果中的非物理跳变或守恒量漂移。这几条合起来给出一个可操作的排查顺序：先看阈值间距是否足够，再看通信步长是否跨事件，最后看 reinit 是否补平了守恒。

## 4. 工程做法与参数

- 阈值来自物理：滞回的两个阈值应取自传感器精度、执行器死区或允许波动，而不是为了跑得快随意放大。
- 最小驻留与光滑过渡：对机械或流体执行器加入最小保持时间或一阶过渡，抑制高频切换。
- 采样控制：用 `sample(start, interval)` 驱动离散控制器，使更新时刻可预测，便于与耦合通信点对齐。
- 事件与耦合点对齐：把事件时刻告知主控方，在其处强制截断通信步长；联合仿真时开启事件模式。
- reinit 后重建一致性：重置状态后立刻重算 ROM 或表的工况标签与内部缓存，避免用陈旧值。
- 事件日志：记录每次事件的时刻、触发条件与被重置的状态，便于事后复现与诊断抖振。
- 分层降阶：对频繁切换的部件优先用光滑特性图，把事件留给真正改变模式的少数切换。
- 事件优先级：当一个时刻同时满足多个 `when` 条件时，明确其先后或互斥关系，避免依赖不确定的执行顺序。
- 单位与标签：把工况标签与表或 ROM 的列定义一一对应，避免切换时读到错误工况。
- 事件计数监控：统计单位时间的事件数与重启次数，异常升高通常是抖振或隐藏事件的信号。

## 5. 可复现示例

一个带滞回的温控切换器，切换后查询 CFD 生成的传热特性表：

```modelica
model ThermostatCoupling "滞回切换 + 特性图切换"
  parameter Modelica.Units.SI.Temperature T_low = 353.15;
  parameter Modelica.Units.SI.Temperature T_high = 373.15;
  Modelica.Units.SI.Temperature T(start = 300);
  Boolean on(start = false, fixed = true);
  Modelica.Blocks.Tables.CombiTable1D fanTable(
    tableOnFile = true,
    fileName = "modelica://Pkg/Resources/Data/fan_heat.txt")
    annotation(choicesAllMatching = true);
  Modelica.Units.SI.HeatFlowRate Q_flow;
equation
  der(T) = 1e-3 * (Q_flow - 5 * (T - 293.15));   // 简化能量平衡
  Q_flow = fanTable.y;
  fanTable.u[1] = if on then 1.0 else 0.0;        // 工况标签: 风机开/关
  when T >= T_high then
    on = true;
  elsewhen T <= T_low then
    on = false;
  end when;
end ThermostatCoupling;
```

用脚本把事件时刻与数据工况对齐检查：

```bash
# 统计表中工况标签（第 1 列）并去重
cut -d' ' -f1 Resources/Data/fan_heat.txt | sort -u
```

验证：画出 $T(t)$ 与 `on` 的阶梯，确认切换只在两个阈值处发生、区间内不抖动；把 `fanTable` 的两个工况值互换，结果应随之改变，说明耦合确实生效。再把通信步长设为跨越切换的长步长，应观察到滞后或跳变，从而确认同步的必要性。

也可做一次“同步压力测试”：把 `T_high` 调到与通信步长边界重合，观察是否出现滞后；若出现，说明需要在事件处强制截断步长。

## 6. 常见坑与排查

- 事件抖振：阈值附近反复切换，仿真极慢；加滞回、最小驻留或光滑过渡。
- `noEvent` 误用：用它掩盖真实不连续，跨过阈值后结果错误。
- 事件与通信步长不同步：长步长跨过事件，输出滞后或突跳；在事件处截断步长。
- reinit 后 ROM 不一致：重置状态却未更新工况标签与缓存，守恒量不闭合。
- 能量不连续：`reinit` 注入的能量无法对应物理过程；检查事件处的能量收支。
- 采样率不当：用过低采样率驱动控制器，漏掉快速过程；过高则事件密集。
- 隐藏事件：连续方程中用了带突变的关联式却未用 `smooth()`，工具隐式生成大量零交叉。
- 事件顺序不定：同一时刻多个 `when` 同时触发，执行顺序依赖工具，结果不可复现；应改写为互斥条件。
- 滞回区间过宽：为省事把两阈值拉得很开，切换迟钝，控制品质下降。

诊断顺序：事件类型判定 → 滞回与驻留 → `noEvent` 审查 → 事件与通信点同步 → reinit 一致性 → 守恒校核。

## 7. 检查清单与参考

检查清单：
1. 每个不连续点都判定为真实事件或分段关联式；
2. 频繁切换处有滞回或最小驻留；
3. `noEvent` 使用处附有“跨阈值也正确”的理由；
4. 事件时刻与耦合通信点对齐，必要时截断步长；
5. `reinit` 后重建了 ROM 与表的一致性；
6. 事件处的能量/质量收支已校核；
7. 采样控制周期与系统动态匹配；
8. 记录了事件日志用于复现与诊断。
